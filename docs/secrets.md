# Secrets model

**Goal:** no credential in Git, in images, in environment variables or in
`docker inspect`, and each system able to reach only its own data.

## Where secrets live

```text
/etc/starter/secrets/            root, 0700 - the only source of truth
├── postgres_password            generated
├── postgres_password.version    "1" - bumped to rotate
├── app_db_password              generated by the app hook
├── app_s3_access_key            generated
├── ...
└── jenkins_git_token            written by a person (optional)
```

1. A stack hook (`deploy/hooks/<stack>.sh`) runs before every deploy of that
   stack. `ensure_secret <name>` creates the value if it does not exist.
2. The file is published as an immutable Docker Secret named
   `<name>_v<version>`, and `<NAME>_SECRET` is exported for the stack file.
3. The stack mounts it at `/run/secrets/<name>` (a tmpfs inside the container).
4. The application reads it from a file: the Go API accepts `DB_PASSWORD_FILE`,
   `S3_ACCESS_KEY_FILE` and `S3_SECRET_KEY_FILE`; PostgreSQL, MinIO, n8n and
   the registry use their own `*_FILE` settings.

Helpers ([`deploy/lib`](../deploy/lib)):

| Helper | Does |
| --- | --- |
| `ensure_secret name [alnum\|hex\|access]` | generate if missing, publish |
| `require_secret name` | publish a value a person wrote; fail with instructions if missing |
| `ensure_htpasswd name user password-secret` | bcrypt htpasswd derived from a secret |
| `ensure_pg_database db role password-secret` | role + database, `CONNECT` revoked from everyone else, password reapplied on each deploy |
| `ensure_bucket_user bucket access-secret key-secret` | bucket + policy limited to that bucket + user |

## Isolation per system

| System | PostgreSQL | Object storage | Other |
| --- | --- | --- | --- |
| `app` | role `app`, database `app` only | user limited to bucket `app` | registry pull via host login |
| `n8n` | role `n8n`, database `n8n` only | none | encryption key |
| Jenkins | none | none | registry push, deploy key with forced command |

Superuser and root credentials (`postgres_password`, `minio_root_password`)
are only mounted in their own servers and used by hooks on the host. Neither
role nor user can administer the server or read another system's data; the
integration tests check it.

## Writing a secret by hand

Never type it as a command argument (it would land in shell history and `ps`):

```bash
umask 077
read -rsp 'value: ' v; printf '%s' "$v" > /etc/starter/secrets/<name>; unset v
```

## Rotating a secret

```bash
cd /etc/starter/secrets
umask 077
head -c 64 /dev/urandom | base64 | tr -dc 'A-Za-z0-9' | head -c 32 > app_db_password
echo 2 > app_db_password.version     # new Docker Secret name
deploy stack app                     # hook reapplies the password, services restart with it
```

- Database passwords: the hook runs `ALTER ROLE` before the new secret is
  mounted, so there is a short window where old connections still work and
  new ones need the new value; the API reconnects on restart.
- Object storage keys: create the new user first or accept a short outage;
  the hook updates the user's secret key.
- `n8n_encryption_key`: **do not rotate** without n8n's export/import, or the
  stored credentials become unreadable.
- `postgres_password` / `minio_root_password`: only used for administration;
  rotate by changing it inside the server first (`ALTER ROLE postgres`, `mc
  admin`), then the file and version.

Old Docker Secrets stay until you remove them: `docker secret ls`, then
`docker secret rm <name>_v1` once no service uses it.

## Backup

`/etc/starter/secrets` is not recoverable from Git. Losing it means losing the
n8n credentials and resetting every password. Keep an encrypted copy outside
the server.

## If a secret leaks

Rotate first, then investigate. Removing a value from Git history or logs does
not undo the exposure.
